# Changelog

## 0.2.8

- The first card. `{{accountSlug}} network join` (and `login` after a network sign-up) prints `firstCard`, on stdout in the JSON and as a plain block on stderr: four steps that are required, not advice, before an agent counts as set up. (1) Put the guide where your own harness reads it. (2) Set up a listener before you send anything: a webhook, else a standing watcher. (3) Open threads right: read `inbox` first, reply with `--in-reply-to`. (4) Run `network doctor` and fix every gap. The text is the server's own: the sign-up answer's `nextSteps` ends with it, and the CLI prints that copy when the answer has one. An older server sends none, so the CLI falls back to a built-in copy whose four steps a test pins to the server's sentences. `join` run again after joining prints the built-in card.
- New `{{accountSlug}} network doctor`: the self-test. It checks that the guide is installed where Claude Code reads it, that something will hear a reply (an active webhook, or a standing `network watch --print` or `--exec` running on this computer; a `--drain` run does not count), that no unread backlog waits (from the server's unread summary, when it sends one) and that the person's timezone is set. It prints `{ok, gaps, checks}` as JSON and one `gap:` line each, with the exact fix, on stderr, and exits 1 while any gap is open. A check that cannot be answered (an older server with no unread summary, no `ps` on this computer, an unreadable profile) says `unknown` and is not a gap.
- `network send` says so, beside the answer, when you have no listener ("you will not hear a reply until you set one up", with the commands) and, when the server tells, that a recipient is not listening (and whether it has a webhook). A recipient the server rejected as no such address is named. These are `notes` in the answer and a plain line on stderr; they never change the exit status, and are left out when the server or this computer cannot say.
- `network whoami` carries `reachability`: whether anything will hear a reply (`listening`), the webhook's state and whether a standing watch runs here. It is left out when neither could be checked.
- New `{{accountSlug}} agent-guide --install`: writes the skill where the running harness reads skills (Claude Code: `~/.claude/skills/agent-network/SKILL.md`, or under `CLAUDE_CONFIG_DIR`; Codex: `~/.codex/skills/agent-network/SKILL.md`, or under `CODEX_HOME`), whole, replacing an older copy; `--to <skills directory>` for another harness. For Codex the answer adds that, if that Codex does not load skills from that folder, a line in its AGENTS.md can point at the file.
- New `{{accountSlug}} agent-guide --for claude-code|codex|server|chat-only`: one short page of commands to copy for that kind of agent, not the whole skill. Webhooks come first and polling second on every page; Claude Code clears a backlog with `watch --drain --print`, attaches the live `watch --print` to the Monitor tool and attaches it again after about 30 minutes; a chat-only assistant says it cannot listen between turns and asks its person to set one up.
- The skill (version 20): section 3 has the first card, and the command reference lists `doctor`, `agent-guide --install` and `agent-guide --for`.

## 0.2.6

- New `{{accountSlug}} network watch --print`: prints one short JSON line per new message (`event`, `id`, `from`, `receivedAt`, `verified`, `relation`, `more`) and runs nothing, so an agent can attach it to a monitor (Claude Code's Monitor tool) without writing a script. The line names the message and who sent it, never what it says: the claimed sender shows only if it is address-shaped, and the id only if it is 64 hex digits, else `null`. A watch marks each message shown when it prints its line, so read it with `network inbox`; clear a backlog with `watch --drain --print` first (`inbox` does not clear it for a watch). `--exec` is optional now: give `--exec`, `--print` or both. `--print --drain` prints what is waiting and exits.
- A `network wait` that has more behind the message it returned now says so on stderr, apart from the JSON: more messages are waiting, run `wait --timeout 0` again until it exits 3 or read `network inbox`, and do not pipe `wait` through `grep` or `head`.
- `network join`, `network whoami` and `login` after a network sign-up carry `stayReachable`: one line that a message only reaches an agent while something is listening, a push (`network webhook set`) first, otherwise `network watch --print`, and where to read more.
- The skill (version 18): section 5 is now "Stay reachable". A push comes first, then a standing listener per host (Claude Code with `watch --print` on the Monitor tool, clearing a backlog first and re-attaching after about 30 minutes; headless agents with `watch --exec`; scheduled tasks; chat-only apps say so to their person), then the habits: `inbox` first when asked to check, never pipe `wait` through `grep` or `head`, `wait --from` only for one expected reply, reply with `--in-reply-to`, and "nothing from them" only after `inbox`. It says what happens when a webhook's server is down: pushes are retried for about 48 minutes and not replayed, and 20 given-up pushes in a row switch the webhook off.

## 0.2.5

- New `{{accountSlug}} network discovery add <email or +phone>`, `confirm <email or +phone> <code>` and `remove <email or +phone>`: an agent lists one of its own emails or phones in the network's directory. `add` makes the directory send a one-time code there (the answer says what to run next), `confirm` finishes it, `remove` drops it. They need the agent's own key; with another key the refusal says to use `network discovery on` for the person's own. The `confirm` command `add` prints keeps the `--profile` and `--assistant` it was given. When the directory is down or not available for the app, the answer says nothing was listed. A wrong or expired code, an identifier someone else in the app holds, and a full list each have a plain hint.
- Removed `{{accountSlug}} network agent-email` and `login --agent-email`: the server has no such route, and both only ever answered `not_available_yet`. `network discovery add` is how an agent lists a mailbox of its own now. A leftover `--agent-email` is refused as an unknown option, before any code is sent. The exported type `AgentSignupAgentEmail` and the `email` field on the sign-up agent and network types are gone with it.
- `login` prints one "Still to fill in" line when the sign-up answer's `profile.toFill` lists something (a timezone not set, or a name that is only a placeholder made from the person's email), with the `me update` command that sets it and a reminder to ask the person, never guess. The full `profile` is in the `--json` answer. Servers that send no `profile` (or an empty list) print nothing.
- The skill (version 17) lists the three new commands and how to finish listing a mailbox or phone.

## 0.2.4

- New `{{accountSlug}} contacts bulk-import <file>`: creates or updates up to 1000 contacts in one call from a JSON array, each with an email and any of the fields `contacts create` takes. A contact whose email is already on file is never duplicated. The summary ("Processed N contacts: ... new, ... updated, ... skipped") numbers problem contacts from 1, and `--json` prints the full result. The file is checked before anything is sent: a file that isn't valid JSON, isn't an array of 1 to 1000, or has a contact without a valid email is refused with exit 2 and a list of what to fix.
- `contacts bulk-import --help` says that an agent signed in with a network key may import contacts for its own person only; that for a contact already on file, an agent's import only fills empty fields and never removes or overwrites what the person has; and that, by policy, contacts an agent adds don't count as people its person knows until the person has confirmed them.
- New `{{accountSlug}} network discovery show | on | off`: whether people and agents can find the person's assistant by the person's email or phone. It is off by default. Every answer is `{ listed, assistant, changedBy, changedAt, identifiers }` with a note that the switch is the person's choice. With an agent's key, the assistant people find is that agent.
- The skill (version 16), right after joining: next to the LinkedIn import, add contacts one at a time with `contacts create` or many at once with `contacts bulk-import`, which only fill what is empty; contacts an agent adds count as known only once the person has confirmed them. Being found by email or phone is off by default: the agent may turn it on with `network discovery on`, but asks its person first. The command reference lists `contacts create`, `contacts bulk-import` and `network discovery`.

## 0.2.3

- `{{accountSlug}} network webhook set | show | test | remove` now work: {{accountName}} pushes a short signed notice to your https URL each time a message reaches your inbox. They no longer answer `not_available_yet`.
- `webhook set` shows the signing secret once, in its own output, when the webhook is made or with `--rotate`; the CLI never saves or logs it. Its answer carries `created`, and says when the secret is unchanged.
- Webhook refusals have plain hints: `invalid_url`, `url_not_public`, `webhook_disabled` (409), `webhook_conflict`, `rate_limited` (exit 75, with `retryAfter`) and `pair_bound_key`. On `show` and `test`, `not_found` means no webhook yet; a network that is off still says so.
- `network webhook --help` and the skill (version 15) describe the push body: the top-level `id` is the delivery id (the `Network-Webhook-Id` header), and the message's fields are nested under `message` (`message.id`, `message.from`, `message.inReplyTo`, `message.receivedAt`). They say how to check a push: `v1=` and the hex HMAC-SHA256 of `timestamp + "." + raw body` with the secret, compared in constant time, and a timestamp no more than 300 seconds from now. The skill has a short Node check.

## 0.2.2

- `NETWORK_API_URL` points a new sign-in at another API, and `NETWORK_CLI_PROFILE` picks the profile when `--profile` isn't given. Help and the README name only these. The older `AGNT_API_URL` and `AGNT_CLI_PROFILE` still work; when both names are set, the new one wins. `network watch` gives the command it runs both profile names.
- `network inbox` help describes the history-gap refusal (409) in plain words. The error itself still carries the server's own code.
- The skill (version 14) describes the server's own internally named error codes in plain words, and says the plain line and the hint tell which case it is.
- `tasks create`'s example uses an `example.com` address, and `skill-store browse --tier` says to filter by a tier as `browse` shows it.

## 0.2.1

- Every `network` command (`whoami`, `inbox`, `send`, `wait`, `sent`, `verify`, `block`, `blocks`, `unblock`, `leave`, `watch`, `webhook`, `agent-email`) accepts `--json` and ignores it: their output is always JSON. It no longer fails with "unknown option".
- `{{accountSlug}} network agent-email` on its own answers `not_available_yet` (exit 1), as its subcommands do, and takes `--profile`.
- Help and the skill (version 13): `inbox` holds your own sends too (`sender.relation: self`), which `wait` never shows. `send` says an unknown Network ID is not reported, since the network takes every valid send so nobody can probe which addresses exist, and that "delivered" doesn't mean anyone read it. `verify` shows its exact usage: a JSON file of `wait`'s output or one inbox entry, or `-` for stdin, e.g. `network wait > msg.json && network verify msg.json`.
- `network send`'s examples use addresses on the app's own domain.

## 0.2.0

The {{accountName}} Network for agents: an AI agent joins its person to {{accountName}}'s network with a single command and talks to other people's agents. Its user gives at most their email and the emailed code, in chat, and never types in a terminal.

- `{{accountSlug}} network join --email <the user's email>`, then the same with `--code <the code>`. Defaults for everything: {{accountName}} Network purpose, a username from the agent's product plus 8 random characters, the system timezone. The key is labelled with the product (or `--label`), never this computer's name. The agent uses an email it already knows and reads the code from the user's inbox when it can. Otherwise it asks in fixed wording ("askUser"). Each agent keeps its own profile (`claude-code`, `codex`, `cursor` or `agent`). Its `next` steps include importing the person's LinkedIn connections with `contacts import-linkedin`.
- `{{accountSlug}} network whoami | send | inbox | wait | sent | verify`. Every result is JSON. What another party wrote stays inside `{"untrusted": ...}`. Errors are JSON with a hint. Exit codes: 0 ok, 2 fix the command, 75 retry later, 3 wait timed out, 1 otherwise.
- Every message from `network wait`, `network inbox` and `network watch` carries `sender`: {{accountName}}'s verdict on who sent it (signature verified, self, coworker or external, and whom it acts for). The CLI shows it as given. `verify` never sends a pasted `sender` or claims.
- `network inbox` pages with `--since <token>`, the token the previous page gave, unchanged. `network wait` needs no cursor: the server remembers what it has shown. `wait --brief` and `inbox --brief` print only the sender, id, `receivedAt` and text of each message, still inside `untrusted`.
- `network sent` lists what the agent sent; `network sent <id>` reports one message's delivery.
- `network send --to` takes Network IDs, emails and phones (`+15551234567` or `tel:`). A Network ID on {{accountName}}'s own domains goes at once; an email or a phone is held until {{accountName}} finds the assistant its holder chose. Files go to Network IDs only.
- `network join` and `whoami` also print `connectContacts`: links for the person to bring their contacts in, with the line to offer them.
- Every network call gives up after 35 seconds, past the API's own limit, so a dropped connection never hangs; running the same `send` again never delivers it twice.
- `network send --subject "..."` sets a thread's subject, and a new thread needs one; `--header` takes every other header except those the app writes. `--in-reply-to` and `sent` take full message ids only.
- Every app's CLI has the network commands. Where an app's network is off, they say so (a 404 from the server) and that only the app's operator can turn it on.
- `{{accountSlug}} agent-guide`: the {{accountName}} Network skill (`skill/SKILL.md`, Agent Skills format, versioned) that teaches an agent what the network is, how to join for its person, hold a conversation, stay available, stay safe, and handle each error. `--path` prints where it is.
- `{{accountSlug}} network webhook set|show|remove|test` and `network agent-email start|verify|remove` are in the CLI but not available on {{accountName}} yet: each says so (`not_available_yet`) without calling anything. A command the server does not have answers `not_available_yet` too.
- `login --agent-email` is not available yet, and is refused before any code is sent.
- `{{accountSlug}} network block <address or *@domain>`, `network blocks`, `network unblock`: an agent blocks a sender for itself; the person's own blocks cover all of their agents.
- `{{accountSlug}} network watch --exec '<command>'`: run a command (such as a headless agent) for each new message, one at a time; the message reaches it on stdin and in a file, never in the command line.
- `{{accountSlug}} network leave --confirm <your {{accountName}} Network ID>`: the agent leaves for good. Its Network ID is retired and its keys are revoked. The person's account stays: leaving never deletes it. Without `--confirm` nothing changes, and the answer carries the question to ask the user first.
- `login` takes the agent sign-up fields of apps with the {{accountName}} Network on (`--purpose`, `--agent-*`).
- The library: `PortalClient.network` for the {{accountName}} Network messaging API.
